## 结论

**目前没有充分依据认为，将本台固件 3.3.0 升级到公开版本 3.3.5，就能通过本体 USB/Fibre 读取实际位置、速度或电流。暂不建议为了这个目的升级。**

这不是“USB 无法反馈”的判断，而是这款产品公开协议与可核实接口的限制。Windows USB 驱动、REF-CLI 上位机、夹爪固件是不同层次；更换传输驱动不会自动为设备增加遥测属性。

| 升级对象 | 当前公开证据 | 对原生 USB 实时反馈的判断 |
|---|---|---|
| Windows WinUSB / libusb 驱动 | 本机已有正常 WinUSB/Fibre 通信，能读设备接口与配置 | 没有因驱动不通导致遥测缺失的证据；升级驱动不能凭空增加设备未导出的字段 |
| REF-CLI 上位机 | 智元与 AGILINK 当前手册仍链接 v1.0.3，与本机已用版本一致 | 没找到更新版通过原生 USB 增加遥测的发布说明；REF-CLI 从设备端点 0 动态获取 JSON，不内置完整设备属性 |
| 固件 3.3.3 | 发布说明新增 TTL 串口支持 | 未声明增加 USB/Fibre 实际位置等反馈 |
| 固件 3.3.5 | 发布说明新增 Modbus RTU；正文新增串口波特率、停止位和协议配置 | 明确的新反馈读取入口在 TTL/RS485 章节，不能推定本体 USB CDC/Fibre 支持 Modbus RTU |

## 官方资料复核

### 2026-09-27：Type-C与TTL/RS485/Modbus的对应关系

重新读取用户指定的中文官方页面。§5.1将CAN、UART_TX/RX、RS485_A/B复用在六针口3/4，§5.2选择物理接口；§6.2通过本体USB-C连接REF-CLI；§6.4标题为“串口TTL/485通信协议”，其中§6.4.1/6.4.2要求通过USB上位机配置串口参数，§6.4.4定义Modbus RTU。故**官方文档支持的TTL/RS485及其Modbus通信路径在六针口，USB-C是可用于配置它们的另一条连接**。不能因为配置命令经USB发送就断言USB端点也接受Modbus RTU帧。

TTL/RS485属于串口电气接口，Modbus RTU是其承载的报文协议，并非第三种独立插口。`modbus_mode`选择串口自定义协议或Modbus；20板从默认CAN切TTL/RS485还涉及硬件焊接跳接，不能只改软件开关。

电脑USB可以通过外接USB-RS485或USB-TTL适配器，再连接夹爪六针口；这不等于普通USB线直接插夹爪Type-C即可传Modbus。USB CDC一般具备承载串口协议的技术可能，但本机COM29映射是否接入Modbus解析器尚未验证，官方页未声明该通路；固件335的Fibre JSON没有位置字段也不能单独证明CDC绝对不支持。此次仅资料复核，未打开COM29或发送探测帧。

Modbus有一项不同于公开CAN控制帧的能力：§6.4.4.2明确可用功能码0x03单独读寄存器20–24（故障、状态、位置、速度、力矩），无需借运动指令触发反馈。这使串口Modbus也适合数据采集；实际刷新率、时延和单位仍需实测。RDK X5+20板优先CAN是利用现有板载硬件和默认跳接，并非VLA只能使用CAN。

2. [智元英文手册](https://www.agibot.com/filepage/265.html)：同样列出 3.3.5 和 REF-CLI v1.0.3。
3. [AGILINK OmniPicker 手册](https://www.agilink-ai.com/OmniPicker/20.html)：同样列出 3.3.5 和 REF-CLI v1.0.3，用于产品资料交叉核实。

两站发布日期口径有差异：智元将 3.3.5 标为 2025-12-23，AGILINK 标为 2025-12-04；AGILINK 的 3.3.3 年份也与智元不同。不能据日期判断它们是不同固件：本轮下载的两站 3.3.5 二进制**逐字节一致**，SHA-256 相同。

Modbus RTU 的寄存器 20–24 分别为故障、状态、当前位置、当前速度和当前力矩。它位于 **Serial TTL/485 Protocols** 下。USB 中配置 `modbus_mode` 的示例，是通过 USB 修改串口协议设置，不等于通过同一 USB 接口传输 Modbus 帧。

Windows 中枚举出的 COM29 仅说明存在 CDC 接口；其与串口控制解析器或状态输出的关系未证实。没有把“COM 口存在”作为 Modbus/遥测可用的证明。

另外，手册链接的 [agillink_omnihand_sdk](https://github.com/AgibotTech/agillink_omnihand_sdk) 当前 README 主要列 OmniHand 型号，未提供足以证明 OmniPicker 原生 USB 遥测的内容；不能借其他灵巧手的 USB 能力推断此夹爪。

## 升级前的工程建议（历史）

1. 保持当前固件。没有看到值得仅为 USB 反馈而升级的证据。
2. 如果要让厂家确认，应明确问：**20 PCBA、固件 330，通过本体 Type-C 的 WinUSB/Fibre 或 USB CDC，是否有读取实际位置/速度/力矩的接口？若有，提供最低固件、属性或帧格式、单位和采样率。** 本轮没有联系厂家。
3. 当前 Studio 只允许经实物定义匹配的 330 写操作；即使未来用户另行决定升级，程序会先进入只读，不能直接假设旧端点编号与接口兼容。
4. 公开 CAN 协议从 3.3.0 起已有状态帧，若需要有文档的算法状态观测，可优先做 CAN 实测；这条路线本身不以升级到 3.3.5 为前提。实际位置语义、速度/力矩换算和时间戳仍需验证。
