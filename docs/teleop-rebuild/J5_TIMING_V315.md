# v315 J5 运动顿挫：时间基准与发送链路诊断

2026-10-19。范围是用户要求的深入核对。读取退役 v313 日志、核对实际发布源码、离线复现并绘图；本轮没有连接机器人控制/反馈端口，没有发送运动，没有修改生产代码、时钟、零位、负载或 Servo 参数。平台保持已释放，用户的官方 SDK 连接不被接管。完整 Goal 仍 paused，自主抓杯取消。

## 结论

已经有明确的平台软件缺陷，不能继续把当前顿挫笼统归因于 J5 硬件或奇异点。主要证据是：固定输入、无模型减速时，生成的目标速度平稳，而目标发送间隔显著波动；控制器自己回报的目标速度和编码器运动也出现波纹。同时存在 v314 已复现的七次保护误停。

目前没有证据支持“上次故障造成时钟或零位失配，需要重新校准”这一解释。应先修复软件时序、执行进度与误判，再用相同接口、轨迹和速度做实机对照。仍不能宣称历史 v304 的初始不跟随已找到唯一根因，或所有工况抖动已经修好。

## 1. 时间基准：没有发现故障后需要人工对齐的证据

控制反馈的新鲜度使用 RDK 收到帧时的 `perf_counter_ns`。求解器 Python 进程与网关在同一 X5 Linux 内核，使用同一单调时钟；C++ steady clock 用于本地耗时。机器人 TimeStamp/RunTime 用于发现重启，不直接与 PC 或 RDK 的墙上时间相减以决定运动。

浏览器与 RDK 通过每个连接自己的四时间戳交换建立输入年龄区间，连接重建后重新采样；PC relay 时间仅用于诊断。1350次交换的往返时间中位15.10ms，P95 57.30ms、最大779.08ms，说明链路/调度也有长尾，但不存在把两个主机的单调时钟原值直接相减的实现。不能靠设置相同系统时间消除这些延迟。

137820帧中：序号无缺口，RDK接收时间、机器人 TimeStamp 和 RunTime 均无回退。设备时间有25个重复值，收包存在批量到达；不能把每帧到达间隔当成精确采样周期。按10秒中位数拟合，两时基表观相对速率约−29.2ppm，残差 P99 6.45ms，最大82.4ms。此数包含设备时间戳更新、网络和线程调度效应，不是晶振标定结果；没有发现需要人工校时的持续重置或时基错用。

另核对27145个周期保存的模型FK一致性诊断：关节反馈经模型计算的法兰位姿与控制器报告位姿，最大差0.0616mm / 0.0258°，没有出现单位、角度零点或坐标定义突变的证据。这只验证两套报告的一致性，不替代独立的实物零位或TCP测量。

**已确认的时间错误在软件读取顺序。** `Executor.tick()` 先取 now，后读取线程更新过的 snapshot；v314 的两次误停年龄为−44.083/−36.750微秒。应在取得快照后读当前时间，并重新校验原截止；不应通过给设备校时、取绝对值或延长旧数据寿命掩盖。

## 2. 发送节拍：目标计算稳定，后续延迟把它变成忽快忽慢

只比较同一 epoch、直接父候选相连的5622对连续动作，排除动作间停顿：

| 时间点 | 间隔中位数 | P5–P95 | 最小–最大 | 标准差 |
|---|---:|---:|---:|---:|
| 求解请求 | 50.26ms | 50.15–51.57ms | 50.00–57.50ms | 0.99ms |
| 求解完成/worker 收到结果 | 50.33ms | 48.62–54.31ms | 21.66–78.96ms | 2.88ms |
| 网关收到候选 | 50.27ms | 41.36–60.09ms | 21.96–80.08ms | 5.95ms |
| 实际 ServoJ 写入开始 | 50.11ms | 33.49–69.28ms | **14.03–108.49ms** | **10.62ms** |

34次发送间隔小于25ms，130次超过75ms；1695/5622对超出40–60ms。约50ms的平均值掩盖了短周期和长周期交替，不能用平均20Hz证明运动平稳。

从每个请求到发送的中位耗时30.39ms、P95 50.67ms、最大83.31ms。其中求解往返中位8.06ms，结果发布/IPC/接收约10.70ms，网关收到后到写口约10.37ms。后两项是阶段边界耗时，不等于纯内核管道传输或单个函数 CPU 时间。

例：候选23435相对上一条的求解请求间隔50.65ms，发送间隔却108.49ms；本条求解往返23.52ms、结果传递15.81ms、网关到写口43.13ms。同窗存在34.10ms的 `executor_tick_with_lock` 阶段和52.59ms的完整控制回调。其他长间隔窗口还记录了状态生成/审计阶段约29ms。当前源码确实让控制 tick、网页状态生成及输入处理共享互斥锁，状态中包含夹爪几何和完整候选元数据；精确到每个函数的 CPU 占比仍需后续 profiling，不能凭阶段标签归罪于某一个库。

`wait_control_cycle(... producer_paced=True)` 在候选事件到来时直接继续，不再以最近一次实际写入约束发送间隔。离线执行与生产哈希相同的函数，确认上一条晚发后，15ms后的下一条就绪事件可以立即放行。**生产者请求等间隔，不代表经过变长计算、IPC、锁竞争后的写口仍等间隔。** 此项是实际代码控制流复现，不是构造机械臂动力学仿真。

不能直接恢复一个独立的 `last_send + 50ms` 等待当作全部修复：它可能再次跳过生产者中间目标。需要统一轨迹推进、采样时间和执行节拍。

## 3. 固定输入窗口排除“只是用户换向或奇异限速”

选定 epoch103 的45个连续目标，持续约2.23秒：输入一直为基座 Z 轴角速度−2°/s，其余为零；status全0，模型碰撞倍率全1，条件数24.88–26.65，低于当前奇异减速起点30，无设备报警。

- 求解请求间隔50.07–50.64ms，标准差0.092ms。
- 求解器 J5 目标速度约−4.56至−4.19°/s，标准差0.0765°/s。
- 实际发送间隔15.33–86.41ms，标准差14.43ms。
- 控制器原始 `QDTarget` 为约−5.61至−3.01°/s，标准差0.467°/s。
- 用设备 TimeStamp 对编码器角度计算40ms窗口速度，约−6.73至−1.99°/s，标准差0.809°/s。它是窗口估计，不能称瞬时真实速度。

使用设备时间戳后波纹仍在，且控制器自身 QDTarget 字段也有波纹；因此不是单纯对抖动的网络到达时间做差分产生的作图假象。另一较早窗口和108ms发送断档窗口也保留，未只展示最极端一帧。

图中“目标步长/发送间隔”只在详细英文图单独展示，它不是实测关节速度；不应把那个较大的数值冒充机械臂真的达到该速度。上述证据确认发送链路不平稳且在设备侧可见响应波纹，尚不能量化发送抖动、ServoJ 插值参数和机械响应各自的因果占比。

## 4. 候选跳过、写口截止及保护误判

完整会话还发现10处同epoch下，后一个已发送目标的父候选并非上一条实际已发送目标。未发送的中间候选仍被用于推进下一步目标。在固定50ms积分下，跳过中间点会把多步角位移压到一次更新中；应以真正执行进度和统一时基管理目标推进，而不是继续累积未经发送的点。

另有4个候选在 `take()` 时尚未过期，但真正写入时超过其原始反馈截止2.79–9.29ms：ID23081、24360、24362、25050。原始已检查反馈在写入时年龄102.79–109.29ms。写口另有新反馈健康检查，但不能延长较早几何证明的截止。这是新发现的写口最终检查缺口，需要一并修复；日志没有证明这4次就是观察到抖动的唯一来源。

v314已确认的7次跟随停止仍成立：

- 5次把尚未执行候选领先实际值约2°判为跟随异常；同帧设备目标与实际仅差0.35–0.47°，前350ms关节仍在前进。
- 2次是先取now、后读新快照的负年龄竞争。

因此要分别处理控制器自身跟随误差、未执行目标领先及真正停滞/指令不连续，不能把它们混为同一个固定角度比较。原v304实际不跟随及跨重置跳变的证据仍保留，修复误判不能让积累目标重新突然追赶。

## 5. 官方 SDK 与 Servo 参数

当前实际调用是官方命令构造器 `Motion.ServoJ`，经 `SubmissionPort -> Dashboard.submit` 唯一写口发送；参数为 `t=0.100, aheadtime=50.0, gain=500.0`，目标生成周期0.05s。

本地固定 SDK 的 `dobot_sdk/api/motion.py:406` 和 `assets/SDK_API文档_完整版.md` 说明默认t=0.1，示例中的50ms循环使用t=0.05。当前参数合法，但运行时间、前瞻和真实发送节拍需要联合验证；默认值不意味着对当前遥操作链路最优。它们不是故障后丢失的时钟校准值。

本次选定窗口中可关联的 CurrentCommandId 首次反馈通常在发送后约21ms出现（采样窗口边缘会影响首次观测，不能当精确执行起点）。此前约134–189ms的位置历史对应延迟，不能直接等同于有同样长度的命令队列；反馈ID、位置插值和真正编码器跟随是不同阶段。

用户官方软件具体采用 Jog、MovJ 还是连续 ServoJ、速度及负载是否一致尚未记录。因此官方测试正常是重要证据，不能替代同轨迹同接口对照，也不能仅凭此盲目改变gain或做零位校准。
