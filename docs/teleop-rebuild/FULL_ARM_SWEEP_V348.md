# 最终平滑目标遗漏整臂碰撞检查：v348 修复候选

## 发现与复现

v346 的 17 次暂停不能全部当成调度超时。其中两组的后续 `official_solver_blocked` 实际为 `collision_snapshot.self_collision=true`，不是新的 deadline 事件：

- deferred-tool-a 首次反馈相交为候选 709；其反馈关节值与此前已写入的候选 705 目标逐位相同。
- inline-tool-b 首次反馈相交为候选 692；其反馈关节值与此前已写入的候选 689 目标逐位相同。

原始执行口是网络隔离的合成设备，150 ms 后反馈已发送目标，本轮没有物理碰撞或实机运动。两次事件不能直接归因为历史实机 J5 抖动，但足以证明当前软件路径存在漏检。

以板端实际参数为源，在 PC 使用同一 URDF、SRDF、原 ACM 和夹爪开度表独立重建；仅把网格资源路径换为 PC 路径，转换后逐字相等。模型依据位于 `evidence/geometry-scheduler-v347/target-collision/model-proof.json`。

原 FCL 全臂查询确认候选 705–708 与 689–691 的目标均存在 **Link3 / base_link** 自碰撞，旧 `DynamicGripper.check` 全部返回 `arm_safe=true`。23 条邻近路径每条检查 65 个插值点，首个相交点分别最早出现在路径的 96.875% / 92.1875%（两组第一条遗漏），后续目标进一步进入相交。夹指组检查全部没有目标碰撞。

源码原因：

1. 官方 Servo 当前姿态碰撞监测只查询请求的实际反馈状态。
2. 输入缩放后还会经过带速度历史的平滑器；反馈落后于已提交目标时，仅对当前姿态缩放并不能证明最终目标安全。
3. 最后一个动态几何检查的组为 `e6_gripper_geometry`，距离证书也只覆盖该组。它会检查夹指对其余部件，却不检查 Link3 对底座。

因此这 7 条目标虽通过原夹指路径检查，在后续反馈进入目标后会触发全臂监测停止。这是具体的遗漏，不是把正常碰撞拒绝本身当作故障，也没有证据将其归因于设备时钟未校准。
