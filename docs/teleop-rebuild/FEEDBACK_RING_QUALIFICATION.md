## 假设与方法

v206 的 252.691 ms 接收等待发生在短抓包窗口结束后；不能凭窗口内良好结果排除 X5 内部问题。此次让独立被动诊断跟随正式会话，覆盖录制、封存、回传与退出。在会话运行期间不批量下载诊断文件。

- 会话 `20261009-142451-14778fd3`；固定 phosphobot、官方 SDK、C++ MoveIt 桥接。未准备控制，无候选或设备写入。
- `capture_feedback_session.py` 核对 shadow owner 和 gateway/camera PID，只读进程计数；使用系统 tcpdump 四个 16 MB 环形文件，tmpfs 存储。不变更调度、内存锁定、CAN 或网络配置。
- 每 50 ms 观察网关和接收线程；每秒读取系统计数并有界读取审计尾部。若捕获就绪后出现 ≥100 ms 的接收／发布或循环间隔，保留后续 10 秒；否则跟随本会话退出。100 ms 仅为诊断触发条件，未修改生产新鲜度规则。
- 分析按包时间合并环形槽位、重组 TCP，以 1440 字节官方反馈 SHA256 匹配。两侧重复载荷均排除；X5 同机时钟括号宽度 0.024709 ms，加入 PCAP 微秒量化误差，不跨主机相减。
- 旧 v206 单文件与故意颠倒槽位的双文件分析得到相同计数及全部延迟统计，37188 等本轮数字不是由旧结果迁移得来。gzip 封装保留原文件 SHA，压缩前后分析一致。

应用审计有两个 ≥50 ms 接收事件：idle 66.770 ms 在捕获开始前；sealing 92.353 ms 完整落在保留 PCAP 内。后者期间网口到达 11 个反馈包，最大间隔 8.854 ms；接收线程有 `futex_wait_queue` 样本，网关 major fault 计数从 101 增至 111，而接收线程 major fault 仍为 1。进程 CPU 仅 8.209 ms，接收线程 CPU 1.416 ms。

**本次 92 ms 等待发生在 X5 接收处理侧，而不是 E6 延迟发送或 PC 无线输入链。** 进程缺页与线程锁等待是相关证据；当前未取得锁拥有者，不能断言具体是 GIL、某个模块加载，也不能外推为 v187 数秒停顿的同一根因。生产模型计数仍保留一次 `feedback_stale`，不能把“未触发诊断”写成所有子系统零异常。

独立采样器在 sealing 初段也发生 901.754 ms 等待，未与 92 ms 接收窗口重合。它包含 SD 卡审计读取与解析，现有时间范围不能细分该次自身停顿；后续应避免把全进程扫描或更密的文件读取当低开销追踪。
