# 官方 MoveIt Servo C++ 接口隔离验证

v175对应无设备原型。v176增加可显式选择的正式C++桥接，并完成正式网页影子验证；默认仍为ROS。尚未取得新接口实机运动资格。

## 假设与改变

v172局部实机记录仍有输入到首发约70–105 ms、首发到实际变化超过0.01°约180–215 ms的延迟。v173发送间隔候选没有明显改善，已撤回。新假设是直接使用固定MoveIt官方C++接口，可减少ROS模式服务切换、轨迹窗口构造与消息回传的起动等待。

探针 `teleop-platform/scripts/servo_cpp_probe.cpp` 改编自固定MoveIt2.12.4提交 `1ade0e9dcf50dbbbc3a984b995c786cf12736235` 的 `moveit_ros/moveit_servo/demos/cpp_interface/demo_joint_jog.cpp`。保留BSD许可证，实际链接官方 `moveit_servo_lib_cpp`，调用 `Servo::getNextJointState`、`resetSmoothing`、`setCommandType`。运动学、碰撞、关节限位与已有独立命名空间的加速度平滑插件仍由上游实现。

本地只添加stdin测试向量和stdout结果、fixture JointState，以及生命周期。没有Dobot SDK、CAN或动作发布者。初版编译成功后，源码检查发现官方Servo构造函数先等待完整关节状态，因此在首次fixture JointState到达后才构造Servo；初版未运行，源码和编译日志仍保存。

本实验直接以20 Hz调用官方API：`publish_period=0.05`、平滑器 `update_period=0.05`；`max_expected_latency=0.2`满足上游至少三个点的参数验证，但探针不构造该未来轨迹窗口。现生产ROS节点内部为100 Hz、`max_expected_latency=0.1`。这是明确的接口与步长候选，不能称同参数的纯性能A/B。

## 测量口径

- 复用现有150 ms一阶虚拟plant及官方KDL模型，目标周期20 Hz。不把虚拟plant响应当E6响应。
- “首个改变目标”是第一份相对虚拟实际关节变化超过1e-9 rad的候选，其耗时包括stdin/stdout。本指标不是正式网页到实际变化超过0.01°的首动指标。
- 持续速度用2–5.8秒窗口线性回归，约束为请求的95%–105%；方向余弦大于0.97；目标关节速度/加速度分别不超过30°/s、120°/s²。所有测试仅在虚拟状态内运行。
- 释放与新epoch以最新fixture状态重置平滑器，清除旧目标。虚拟立即停止不代表真实Stop或制动时间。
- 相同X5内核单调时间，未比较跨主机时钟。每次输入、候选、官方状态、时长及虚拟实际关节均保存。

### 生产桥接参考组失败

随后运行当前生产ROS桥接的32次起动脚本，尚未进入第1次输入就在40秒启动期限内无法ready，exit1。`baseline/worker/servo.log`记录Servo构造成功，但一直等待robot state update；模型核对已通过、状态码始终为空，未发输入。原失败及正常清理日志保留，不记成“旧方案延迟40秒”，不据此计算性能提升倍数。

参考组真正使用的参数位于 `baseline/worker/params.yaml`。外层helper也生成了未使用的 `baseline/params.yaml`（C++配置），保留原文件但不能将它当作参考组配置。

源码证据：固定上游 `servo_node.cpp` 起动循环等待 `PlanningSceneMonitor::getLastUpdateTime()` 晚于线程起点；`current_state_monitor.cpp` 对相同位置更新接收时间，但只在关节值改变时调用场景更新回调。因此在第一份静态fixture恰好早于servoLoop起点时，会缺少后续场景位置变化。此失败与该起动竞态一致；没有添加假关节噪声或发设备动作来绕过。直接API探针等的是完整JointState及其接收时间，三组在相同静态fixture下均可起动。

### 取舍

新接口的隔离结果足以支持下一步正式适配，不再进行发送间隔盲调。当前生产实现保持不变；该探针仍无生产租约/反馈截止期，禁止直接连接设备。正式适配需保留网关单一控制所有者与独立Stop/反馈路径，增加直接API来源记录、反馈时效、epoch切换、子进程退出和正式页面影子验收。现有C++结果不能跳过这些环节。

即便隔离全部通过，仍需正式适配的来源、新鲜度、停止/清理语义以及网页影子验证；后续实机仅能使用已走过的局部路线。不能因为本实验起动改善就宣称200/400 ms响应、最终速度或完整平台已交付。

## v176：正式适配与网页影子

`servo_cpp_adapter.cpp`延续上述官方demo和许可证，实际调用同一官方库、模型与平滑器；没有设备SDK、CAN或动作发布者。`jazzy_cpp_worker.py`仅管理一个在途计算、最新反馈/输入和归属子进程。网关继续独占动作与Stop，原始反馈不依赖计算进程。`--moveit-api cpp`为显式选项，默认ROS及原制品清单保持。

每一步保存原输入接收时间、计算派发/完成时间、原SDK反馈时间、平滑器种子位置/速度和父候选ID。释放、新epoch及反馈generation变化后清除旧候选并以实际状态重置。模型/FK误差仍按1mm/1°检查；异常只使候选不可用，不结束独立反馈读取。计算须在50ms内完成，消费使用原反馈100ms与原输入250ms的较早期限，每个候选只消费一次。

首速度组曾额外设置50ms候选租约，两个独立20Hz循环相位错开导致22次sample_deadline及最大1.002959s空档。保留`speed/`原失败；修正为上段原始时效约束，不延长输入或反馈期限、不追赶周期。`speed-r2`四组速度比0.955947–0.975930、最大更新空档62.181ms通过既定95%–105%虚拟判据，仍有实际调度开销，不宣称严格请求速度。
