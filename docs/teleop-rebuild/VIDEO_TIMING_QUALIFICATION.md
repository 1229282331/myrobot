# 无线预览测时与编码并行：v91–v92

2026-10-08，基于 `e1bed7e`。正式 phosphobot 页面、PC↔X5无线、Gemini E真机画面；两次会话均为未准备的shadow，机械臂运动/Stop/Enable/CAN均0。没有执行夹爪动作、改参数或下机。完整遥操作 Goal 尚未交付。

## 方法和修改

沿用固定 OpenCV 4.11.0 QRCodeEncoder、jsQR 1.4.0 和 MediaMTX 官方WebRTC reader。给正式启动器补齐可选`latency_marker`开关，默认关闭。默认原图、预览码率900k、640×360、20Hz以及控制路径不变。

旧测时文案仍写“SDK接收”，但v77之后RGB已经采用UVC内核接收起点。本次在**诊断预览的像素**中明确记录源接收类型、完整capture_epoch、帧号和毫秒时间：`E6K`为UVC内核接收，`E6S`为SDK等待返回。元数据中各SDK字段和UVC PTS保持原样；没有把深度或RGB声明为曝光同步。

浏览器在`requestVideoFrameCallback`中识别实际视频画面二维码，终点采用`expectedDisplayTime`。四时间戳往返测时给出时钟偏移区间，不假设无线往返对称。每条样本保留偏移边界、完整测时往返和时间年龄，增加1ms源时间量化及1000ppm相对漂移预算。漂移预算包含测时往返本身。此方法测的是**UVC内核收到RGB至浏览器预计呈现**；未测传感器曝光到内核的USB前段，也不是显示器光子测量。

报告同时保存所有尝试、二维码识别失败、时钟尚不可用、每约2秒实际呈现帧数/时长/解码丢帧。离线重新计算每条时钟区间和帧率；P95/P99用与界面相同的nearest-rank算法。未删除慢帧、首个呈现窗口或失败样本，未把平均值冒充P95。

## v91 失败与最小复现

会话`20261008-044109-56c0fe21`。源RGB约29.588fps，但预览平均14.890fps，P95上界327.869ms，均未达到目标；75个呈现窗口中55个低于15fps。初始短读数约264ms不替代最终失败。全会话预览队列丢弃1048帧，源流仍正常；原报告、图像和会话完整保存。

关闭会话后，在X5上用同一份已保存JPEG离线基准复现：解码缩放P50约26.124ms，新完整二维码P50约38.599ms，串行合并约65.008ms，解释了约15fps瓶颈。这个基准不打开相机、E6或CAN。

只改变预览线程内部的任务安排：使用标准库`ThreadPoolExecutor(max_workers=1)`，把该帧的二维码生成与该帧JPEG解码缩放并行。最多一帧和一个QR任务在途，等待该任务后拼入同一图像；不缓存旧二维码、不替换帧时间、不建立历史任务队列。正常无测时标记的预览不创建该线程池。相同离线数据并行P50/P95/max为38.774/39.033/39.747ms，支持进行正式复测。
