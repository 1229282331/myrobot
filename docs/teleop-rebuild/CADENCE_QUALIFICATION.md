# 发送节奏候选对照（v173）

2026-10-09。结论：**不采用本次“从真实发送时点再等待一周期”的调度改动**。已恢复 b0e271c 的生产调度；没有部署到实机或发送设备命令。

## 假设、改变与结果

保留的 v172 两个局部 J6 片段中，组内10个间隔有6个短于50 ms，最短20.416 ms、最长163.126 ms；v170有13个间隔，最短48.704 ms。命令ID在新反馈中很快出现，不能据此宣称目标完成，但这些片段不支持每条 ServoJ(t=.1) 必然排队100 ms的猜测。原ACK、ID、QTarget、QActual与X5接收时钟逐项保存在 `evidence/cadence-v173/dispatch-v170.json` 和 `dispatch-v172.json`；不混用PC时钟、不改变原首动阈值。

候选只改变普通循环的下一次起点：不得早于上一发送＋50 ms。释放/Stop仍在等待锁之外。93专项通过并不代表产品效果通过，因此在X5独立环境运行同源A/B，四组均无E6/CAN连接，完成后进程与proc挂载释放。每一对源码manifest仅gateway.py不同，SHA与判断保存于decision.json；候选完整源码保留于归档。

静态反馈实验只用于负载与调度；不能作为运动速度证据。虚拟plant按原生产桥接与时间采样，证明目标速度没有因减小发送频率而同比下降，但不证明真实控制器运动、响应、停止或网页链路通过。其5ms轮询也计入间隔，不假称精确硬实时20Hz。

## 决策与下一步

候选消除了短间隔，但实际更新频率更低，第一候选响应没有明确改善；不把速度比通过当成整体改进。历史v70已出现相似退化，本次对照后不继续往实机推广该方案，也不通过缩短名义周期补偿它。

生产控制保持原版。后续优化应在保持20Hz目标、输入/Stop可独立处理的前提下处理计算和发送的耦合；必须有新最小复现与同条件证据，不再次来回修改这一等待策略。所有实机复核仍只能走用户已验证的局部路线，不扩展线缆扫掠。
