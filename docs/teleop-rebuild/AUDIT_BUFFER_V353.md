# V353 记录缓冲及启动等待的联合调整

本轮沿用用户对人为预算联合调整的授权。55/70 ms 的计算/请求候选不重新编译；在 V352 联合负载暴露的录制故障上，增加有界记录缓冲，并区分冷启动等待与运动中的反馈期限。当前不是实机验收完成。

## 正式源码修改

- `audit.py`：原始反馈队列 2,048 → 8,192 帧，125 Hz 下约 16.4 → 65.5 秒；事件队列 2,048 → 4,096。原始载荷上限约 11.25 MiB，另有对象与事件内存。只缓冲证据，控制继续读取最新反馈，不补发旧运动。
- Audit 父进程失败时先关闭私有管道，给子进程至多 3 秒封存部分日志并返回计数；保留原错误。子进程不能返回回执时，`writer_receipt_received=false`，不把初始零计数当完整结论。
- `audit_writer.py`：异常 EOF 或渲染错误仍携带已经处理的计数，原失败不会改成成功。
- `launcher.py`：冷启动默认等待 60 → 120 秒，配置 `startup_timeout_s` 接受 10–300 秒有限数值。启动仍须满足原反馈新鲜度、相机、模型和配置一致性判据；失败保存最后状态与实际等待时间，成功保存启动用时。

补丁与原件：`output/audit-buffer-v353/{baseline,source,audit.patch,startup}`。两组补丁均逐字节重放核验。未修改设备负载、TCP、夹爪、模型或 ACM；未切换正式原生二进制。

## 新测量

原有正式代码配合三路合成记录器与一次原生启动，在网络隔离下完成。331 次合成运动发送无暂停、过期发送或跟随停止；被动记录器 7,395 帧、1,184 事件完整。没有复现 V352 的长溢出。
