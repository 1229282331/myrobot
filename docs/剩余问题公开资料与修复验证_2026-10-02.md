## RGB时间戳：具体原因与修复

实物仍是SDK回读的Gemini E、SN `AY4A1520111`、固件RD3481、RGB PID055c/深度065c。不能套用其他型号固件。

1. X5读取RGB USB描述符：UVC1.00，`dwClockFrequency=15000000`，即15MHz。该时钟是实机描述符读数。
2. 从SDK官方C API `ob_frame_metadata`/`ob_frame_metadata_size` 获取原始Linux UVCH块，按Linux6.1文档解析内核接收ns、SOF和UVC payload PTS。
3. 20秒对照446张RGB，446/446满足SDK毫秒值等于32位PTS、SDK微秒值等于PTS×1000。例如PTS `0x989adae5=2560285413`，SDK us=`2560285413000`。实际应按15MHz换算，不能把这个计数直接当毫秒。
4. 320秒长测7773张SDK原始us精确等于展开计数×1000，另52张少1us；全部在1us内。该细微舍入不改变15000倍单位问题。SDK自身已展开本次回绕，但单位仍错误。

因此“除15000”有本台直接证据基础；正式代码使用原始PTS与实读描述符频率独立换算，避免静默覆盖SDK字段或硬编码其他型号时钟。只切换V4L2并不会修复SDK原时间字段。

新增 `dcw/tools/uvc_clock.py`，`camera.py` 的可选 `uvc_pts=True` 和 `rdk_healthcheck.py --uvc-pts`。代码只对Linux Gemini E按SN匹配RGB描述符，保留所有SDK原字段，新增：

| 字段 | 语义 |
|---|---|
| `uvc_pts_32` | 一帧UVC payload的原始uint32 PTS |
| `uvc_pts_unwrapped` | 连续采集内按模差展开后的设备计数 |
| `uvc_pts_clock_hz` | 实读UVC描述符时钟，本台15000000 |
| `uvc_pts_ns` | 展开计数×1e9/时钟频率，整数ns |
| `uvc_pts_wrap_count` | 本次采集已观察到的回绕次数，含预热 |
| `uvc_kernel_receive_ns` | UVCH中内核CLOCK_MONOTONIC接收时刻 |
| `uvc_pts_available` | 本帧是否有可解析metadata；缺失时不补造时间 |

启动时发现某些RGB帧metadata为空，初版严格解析因此中止；失败证据保留。修正后仍保留这些图像，PTS标不可用。损坏、同帧PTS不一致、payload error、逆跳/重置或超过3秒的不连续仍会中止，不重连续写旧时钟。

320.003秒720p双流结果：RGB7825张全部解码/全部有PTS，深度9607张全部含有效值，两路帧号缺口0，队列峰7/128，无接收、处理或清理错误。

- 32位15MHz计数约286.331秒回绕，实测一次。帧1407→1408：PTS `4294849295→629555`；展开计数 `4294849295→4295596851`；正确ns `286323286333→286373123400`，继续单调，间隔约49.837ms。
- 7825张正确字段全部满足整数换算式，严格递增。
- 首末比为1.000626，启动积压影响首点；排除前5秒后，正确时钟对主机线性拟合斜率1.000107083，对内核接收时钟1.000107009，约107ppm差异。主机拟合绝对残差P99约2.279ms，仅描述本轮设备时钟与接收时序。
- 内核到SDK返回的延迟中位32.332ms、P99 36.966ms、最大200.923ms，说明主机接收时间不能直接当曝光时刻。

**修复范围是时间单位和连续回绕。** PTS是否对应曝光起止、RGB与深度时钟关系、机器人反馈同步均未标定。该字段不是UTC或X5时钟。Windows路径未验证，LibUVC metadata结构未验证，默认均不启用。本台global timestamp/帧同步不支持的记录没有被这项修复推翻。

证据：`timestamp_metadata20_frames.jsonl`、`timestamp_root_analysis.json`、`uvc_corrected320_frames.csv`、`uvc_corrected320_report.json`、`correction_verification.json`。

## 1080p：应用处理改善，30fps仍未通过

X5已有OpenCV4.11.0使用libjpeg-turbo3.0.3、NEON，并非缺少JPEG加速库。10张本机1080p JPEG的70次计时，OpenCV中位37.945ms，系统TurboJPEG普通模式36.540ms，输出像素完全一致。FASTUPSAMPLE约32.605ms，但有像素差异，因此未采用这一选项。

新增1–4个可选解码worker，默认1；实机用2。独立接收线程继续记录每帧，待完成解码有界为2×worker，按原接收顺序消费，保留图像/帧号/时间戳配对。快照单独异步保存，最多一个未完成任务。坏图、队列满、缺流仍报错，无静默抽帧或丢弃。新增 `processing.csv` 保存逐帧解码耗时与接收到完成的延迟。

| 配置 | RGB/深度实收 | 实收fps | RGB全部解码 | 队列峰 |
|---|---:|---:|---:|---:|
| V4L2，1080p双流60秒，2worker | 1473/1806 | 24.552/30.081 | 1473 | 9/128 |
| 原配置LibUVC，1080p双流60秒，2worker | 1482/1806 | 24.682/30.095 | 1482 | 8/128 |
| V4L2，720p双流320秒，2worker＋PTS | 7825/9607 | 24.450/30.019 | 7825 | 7/128 |

三组实收与处理数量一致，帧号缺口0、所有深度帧含有效值、无应用接收/处理/清理错误。1080p解码中位42.377/42.544ms，接收到完成P99 158.690/144.761ms。并行线程解决本轮单线程处理能力不足造成的应用队列积压，**没有证明1080p30fps或严格实时延迟**。

此前720p/1080p抽样约29.7–29.9fps，本轮两后端均约24–25fps，不能唯一归因于V4L2。AE=true、RGB曝光回读157、gain0；未做受控照明、逐帧曝光或USB包级对照，低帧率原因仍未定位。后续先做固定光照下RGB单流/双流、同曝光设置与后端的受控对照，再判断光照/曝光、传输或SDK组帧影响。本轮不写曝光属性。

SDK启动与停止仍有内部队列和异步取消警告；日志保留，计时阶段帧号无缺口不代表SDK内部从未丢弃过帧。最终原LibUVC收尾又出现RGB控制接口绑定、流接口未绑定；确认无采集进程与USB占用后，仅重绑定已核实RGB控制接口恢复。没有整USB总线复位。V4L2收尾两接口正常绑定，是后续更易管理的路径，但须继续检查实际帧率。

官方D-Robotics `hobot_codec` 支持JPEG→NV12，可作为后续降低CPU的候选。其README性能表并非本台X5实测，不能套用；本轮没有部署ROS2/硬件解码。当前改动已在既有软件环境内完成验证。

## IR固定亮点：需要实物排查

历史与安装后原始图的固定位置为512×384 `(352,212)`、1024×768 `(704,424)`；最新均1023，邻域约31。跨场景、两种原分辨率都有，不能仅归因于预览缩放，但还不足以认证物理坏点。

已查Orbbec官方SDK/固件清单、GitHub issue和Gemini E社区资料，未找到本型号针对固定IR亮点的已确认修复、坏点校准入口或可直接升级的固件。Gemini E flickering帖子只有提问，不能当修复方案。

建议实物验证顺序：先在不改变安装与安全保护的前提下，用均匀漫反射平面检查亮点是否随纹理/光斑变化；再由现场仅遮挡接收镜头取得暗场，避免触及/遮住激光保护区域；记录原生IR与曝光/增益。若需固定曝光对照，应先保存参数并按明确实验范围执行，不能通过关闭LDP/提高激光绕过保护。暗场与均匀场仍固定异常后，提供SN/固件、原图和曝光值请厂家核查。

软件只能在后续明确验证后标记无效像素，不能修好传感器或凭一个IR像素推断全部深度误差；本轮未mask、未补造深度。若确认为固定硬件异常而无厂家校正路线，维修/更换相机才是彻底处理。

## E6与夹爪：哪些需要现场或厂家证据

历史J4回落发生于尚未装本套末端的阶段：多姿态下使能后约4.7°、9.5°、13.4°，使能闭环保持正常。这说明不能只把问题归因于新末端太重。E6官方V1.4 §8.2要求电机下电时各关节或工具端不掉落；未找到本机J4无抱闸变体或确定固件修复。通用V4的 `BrakeControl(axis,0)` 是改变抱闸状态的命令，不是只读查询，也不是维修方法，本轮未调用。

本地整理的厂家核查内容：按本机序列号/硬件版本确认J4/J5是否配置制动器；确认允许回落量与正常制动时序；检查制动器保持力矩、供电/驱动、传动连接与减速机间隙；按厂家规程在有效外部支撑下检验。未对外发送。软件保持使能或寻找新park姿态不能替代断电保持能力验收，不能以反复开关使能的远程实验代硬件检修。

完整末端的质量与重心仍需实称/几何测量。控制器反馈Load0.75kg、Center0只是设置参数；未找到确认适用于本台E6的只读实称入口。750g仅适用于手册负载曲线规定的重心距离，不能以预算质量断言抓取余量。TCP当前Tool0/偏移0，先定义夹爪抓取参考点，再依据实际装配几何或标定建立工具坐标；需要实际尺寸数据，不能猜一个指尖偏移写入控制器。

夹爪由E6腕部供24V，已有低速空载通过证据，但腕部额定/峰值电流与线缆压降未验收。底座电源2A或DO单路0.5A资料不能自动代表腕部容量。下一步应查本机腕部接口额定容量，现场测启停/夹持时端电压及电流，再决定供电；不要由通信正常推定满力/堵转供电正常。

夹爪首个15%命令返回state2后，用户确认正常张开；官方§6.3规定收到命令立即反馈，支持“第一帧可能在运动前”的解释，但不能确定该帧原因。本轮保留原state2保护，没有改为忽略堵转，也未补发夹爪命令。
