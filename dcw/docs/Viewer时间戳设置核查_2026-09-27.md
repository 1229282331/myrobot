# Viewer 时间戳设置核查

公开资料后续复核见 [时间戳异常公开资料复核](时间戳异常公开资料复核_2026-09-27.md)：Windows UVC metadata注册值得检查但本机状态未读出；官方公开 `timerSyncWithHost` 实现仍依赖1037，不能把改接口名当成修复。v1.10.37仍为v1最新发行，Gemini E的v2升级仍列未来计划。

针对用户提出的“官方 Viewer 有时间戳设置，是否需要开启”核对本地官方 Viewer v1.10.37、同版本 SDK 头文件/配置说明及已有日志。初次核查窗口清单没有发现运行中的 OrbbecViewer；随后用户明确点击“时间戳同步”，反馈了下述错误。助手本轮未启动 Viewer、未新开相机流、未重置时钟或修改设置。

## 用户手动同步结果（最新）

用户提供的原始日志：

```text
#60 [ERROR] Sync device time failed. ob::Device::syncDeviceTime, Property is not supported! propertyId: 1037
```

官方 `SDK/include/libobsensor/h/Property.h:465–468` 定义 `OB_STRUCT_DEVICE_TIME = 1037`，注释为“get/set device time”。1037 是设备时间属性标识，不是相机硬件故障码。此错误明确说明：当前 Gemini E / RD3481 / SDK v1.10.37 组合不支持 Viewer 这次调用所需的属性，同步请求失败；不能解释为同步已开启但尚未生效。

`SDK/include/libobsensor/hpp/Device.hpp:426–430` 将 `syncDeviceTime()` 定义为把本机系统时间同步到设备，并标记为 deprecated、推荐 `timerSyncWithHost`。这里只确认该旧接口路径不支持，未实测替代接口，不据此宣称所有可能的校时路径均不支持，也不保证换新接口或升级固件即可解决。

这条日志确认用户所指的“时间戳同步”按钮当前不能完成校时；不证明相机硬件损坏，也没有定位此前 RGB 时间戳约15000倍增长速率的根因。错误原文作为用户报告单独保存在 `evidence/viewer_timestamp_20260927/user_sync_error.txt`。

## 已核实

- Viewer 程序包含 `Timestamp Synchronization`、`DeviceClockSync`、`Timestamp Reset`、`Device Timestamp`、`Global Timestamp`、`System Timestamp` 等文字。来自程序静态字符串，不代表本次已看到这些控件的实时状态，也不代表每项都适用于 Gemini E。
- `vendor/orbbec-v1.10.37/viewer/config/config.ini` 的 `IsDeviceClockSyncFirstConnected=true`，`AutoClockSyncInterval=120`（分钟）。Viewer SDK 日志在 **17:14:32.385035** 记录 `Enable multi-device clock sync, repeatInterval=0ms`。这证明程序触发过一次同步调用，不证明该机型实际完成了设备校时。
- SDK `Context.h:86–92` 明确：时钟同步用于同步主机与已创建的设备，限定 **if supported**；间隔 0 表示只执行一次。因此目前不能把异常解释为“忘记勾选同步”。
- Viewer 与采集脚本使用的 SDK XML 中 `GlobalTimestampFitterEnable` 都已为 `true`。官方配置说明 `OrbbecSDKConfig_v1.0_CN.md:60–90` 描述的是通过回归把设备时钟转换到主机时间域，主要支持 Gemini 330 等系列；此前实机 `health_20260927_152958_391976/report.json` 中 `global_timestamp_supported=false`。不能用通用配置开关推断 Gemini E 获得此能力。
- `Frame.h:83–91` 说明：不支持全局时间戳的设备，该全局时间戳接口返回 0。它与普通设备时间戳、主机接收时间是不同字段。
- Viewer 17:14 的日志还记录 `enable frame sync failed!`，对应 SDK 的 `Current device does not support frame sync!`。此处指当前 SDK 帧同步功能，不应扩大解释成对所有硬件同步能力的完整审计，也不能与设备时钟同步混为一谈。

## 各选项与当前问题的关系

| 选项 | 作用及本机边界 |
|---|---|
| Device Timestamp | 设备时间字段；此前实测 RGB 字段按标称微秒解读的增长速率约为真实时间 15000 倍，当前不能直接作为时间基准。 |
| System Timestamp | 主机接收帧的时间；此前速率正常，可作软件配对依据，但包含传输/缓存延迟，不能当作曝光时间。切换显示来源不等于修复设备字段。 |
| Global Timestamp | 设备曝光时间向主机时间域的转换，需要机型/SDK支持；此前该设备查询不支持。 |
| Timestamp Synchronization / DeviceClockSync | 在支持的设备上校时。用户手动点击“时间戳同步”已返回 `syncDeviceTime` 所需属性1037不支持，故这次同步明确失败；此前自动时钟同步调用是否适用、替代接口是否支持未独立实测。 |
| Timestamp Reset | 重置计时起点；即使支持，单纯改变起点也不能纠正15000倍的增长速率。当前未执行。 |

当前结论：用户指定的“时间戳同步”按钮调用已明确因属性不支持而失败，不能靠重复点击解决，也不应因为此错误认定二手硬件损坏。原型继续保存原始字段与主机高精度接收时间；不直接除以15000、不把系统时间标签当作硬件同步。今后如验证其他有支持依据的路径，应以前后连续帧时间增量及主机计时作对照，而非只看界面显示了一个时间数值。

## 证据

本轮选取的配置与日志摘录保存在 `evidence/viewer_timestamp_20260927/`。该日志为用户本机已有 Viewer 运行产物，不能冒称由本轮自动操作产生，也没有根据仅两条首帧日志计算精确时钟速率。
