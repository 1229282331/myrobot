# RGB 时间戳异常：公开资料复核

日期：2026-09-27。目标设备为本机识别的 Gemini E / RD3481，Windows 11，OrbbecSDK v1.10.37。已知实测是 RGB 设备时间字段按接口标称微秒解释，增长速率约为主机时间的15000倍；用户手动点击 Viewer 时间戳同步返回属性1037不支持。

本轮检索了 Google 公开索引、Orbbec 官方 SDK 文档/发布记录/GitHub issues、官方开源实现，以及 RTAB-Map 的相关讨论。没有找到与本机“Gemini E + Windows + RGB约15000倍速 + 属性1037不支持”完全对应、且已被确认修复的公开案例。以下将直接证据、可排查方向和不能套用的案例分开记录。

## 结论与新线索

1. **Windows UVC metadata 注册是官方明确要求的环境准备步骤，值得核验，但尚未证实是本机根因。** 官方文档说明，不注册可能造成设备时间戳异常并影响帧同步。注册 metadata 是让 Windows 提供帧的附加信息，与向相机写入当前时间的“时间戳同步”按钮不是一项操作。本机RGB接口为UVC（PID055C）；官方脚本按VID2BC5筛选，不只针对某个新型号，因此该接口值得检查。脚本覆盖设备不等于注册后一定修复本机时间戳单位。
2. **不能把更换 `timerSyncWithHost` 名称视为确定解决办法。** 官方当前公开实现的这个接口仍通过 `OB_STRUCT_DEVICE_TIME` 读写设备时间，亦即1037。此源代码来自SDK v2，不是对闭源v1.10.37内部实现的证明，但足以否定“只因旧函数弃用，改名就一定好”的推断。
3. **官方确实承认过SDK时间戳单位实现错误，但不是本机同款案例。** SDK v2.1.1/Femto Bolt/C# 的 issue #37 中，维护者确认毫秒接口错误地返回微秒，需要补 `/1000`。本机使用v1.10.37的C微秒接口，速率异常约15000倍，不能直接套用该修复或除以1000/15000。
4. **目前没有已确认适用的简单升级路径。** 官方v1最新release仍为本机使用的v1.10.37；发布说明新增的是DaBai/Gemini E的Linux UVC后端选择，未列出这项Windows时间戳修复。SDK v2当前README仍把Gemini E和DaBai DCW的OpenNI→UVC升级列为未来计划，不能直接替换SDK或借用其他型号固件。固件仓库当前README未列Gemini E的可用升级包；这只是公开清单的结果，不代表厂家内部没有固件。

## 主要来源与适用边界

### Windows metadata

- [SDK v1官方Windows环境说明 §3](https://github.com/orbbec/OrbbecSDK/blob/7fa1485e751a779c4c845089c5b9721faaddd959/doc/tutorial/English/Environment_Configuration.md)：UVC获取时间戳等metadata需要注册表注册。
- [官方注册脚本](https://github.com/orbbec/OrbbecSDK/blob/7fa1485e751a779c4c845089c5b9721faaddd959/misc/scripts/obsensor_metadata_win10.ps1)：检查两个设备接口类下的VID2BC5实例，设置 `MetadataBufferSizeInKB0=5`；部分多pin型号另设置1/2。它不是校时命令，也不会让本不支持1037的固件自动增加此属性。
- [官方SDK v2 README Windows准备说明](https://github.com/orbbec/OrbbecSDK_v2/blob/b71adc7d48f7b77d5937b012e0153f25a0461c0d/README.md#L305)：明确警告未注册metadata可能导致设备时间戳异常。
- [SDK v1 issue #25](https://github.com/orbbec/OrbbecSDK/issues/25)：Femto Bolt在自研程序中时间戳为0、Viewer打开后可用；贡献者指向README配置，提问者确认解决。型号与“全0”症状均不同，仅作环境准备遗漏的相关案例。

本轮尝试用PowerShell只读枚举上述两个接口类、仅筛PID055C，收到 `Requested registry access is not allowed.`。没有取得足以判断注册是否存在的完整结果，**不能写成“已发现没有注册”**。未改注册表、未修改PowerShell执行策略、未运行官方安装脚本、未提升权限。

### 校时接口仍依赖1037

[官方 DeviceClockSynchronizer.cpp](https://github.com/orbbec/OrbbecSDK_v2/blob/b71adc7d48f7b77d5937b012e0153f25a0461c0d/src/device/component/timestamp/DeviceClockSynchronizer.cpp#L86) 中 `timerSyncWithHost` 在114行写、126行读 `OB_STRUCT_DEVICE_TIME`。本机v1头文件定义1037即此属性；用户Viewer错误直接证明那次调用未成功。当前尚未调用替代接口，公开v2实现也不能直接等同本机v1二进制。

### 已知单位错误案例

[官方 issue #37 维护者答复](https://github.com/orbbec/OrbbecSDK_v2/issues/37#issuecomment-2635942162) 明确指出v2.1.1毫秒接口漏除1000。其对应条件是Femto Bolt、Windows11、C#、毫秒/微秒接口混淆。本机用C API `ob_frame_time_stamp_us` 和64位无符号返回，单位及版本不同。此案例支持“时间标签异常可能出在软件实现”，不证明本机已定位，也不构成比例修正授权。

### OpenNI时间字段的主机替代

[官方 OpenNIFrameTimestampCalculator.cpp](https://github.com/orbbec/OrbbecSDK_v2/blob/b71adc7d48f7b77d5937b012e0153f25a0461c0d/src/device/openni/OpenNIFrameTimestampCalculator.cpp#L13) 的公开实现同时把设备和系统时间字段设为主机当前时间，并标记 `setDeviceTimestampFromHost(true)`。这说明在该SDK路径中，“设备时间字段”也可能是主机替代值，与本机深度两个字段逐帧相等的观察相容；不能据此断言本机闭源v1走同一实现，更不能把它当硬件曝光时间。

### 升级与其他讨论

- [官方v1.10.37发布](https://github.com/orbbec/OrbbecSDK/releases/tag/v1.10.37)：API的latest查询仍返回这个版本。Linux后端切换是可供后续跨平台对照的路线，未在本机执行。
- [官方SDK v2升级计划](https://github.com/orbbec/OrbbecSDK_v2/blob/b71adc7d48f7b77d5937b012e0153f25a0461c0d/README.md#12-upgrading-from-openni-protocol-to-uvc-protocol)：Gemini E/DCW仍在未来升级表中。代码里存在OpenNI公共组件不等于特定型号已被正式支持。
- [固件公开清单](https://github.com/orbbec/OrbbecFirmware/blob/696b3d10960aa0629c92a0474c50114bfac52270/README.md)。
- [RTAB-Map #1324](https://github.com/introlab/rtabmap_ros/issues/1324)：同为Gemini E，但为ROS数据接收问题，维护者能正常回放所提供bag，未给出本机Windows/15000倍速的解释。
- [RTAB-Map #1360](https://github.com/introlab/rtabmap_ros/issues/1360)：讨论接收间隔与图像时间标签不一致造成处理丢帧；型号未对应、数量级不同，不能认作同一故障。

## 推荐后续验证顺序

1. 在能够读取所需注册表项的权限下，先导出/核验PID055C的metadata注册值；若确实缺失，再以可恢复的、仅针对该设备的改动补齐并按要求重开流/重插，然后做相同配置前后对照。当前仅调研，未执行任何写入。
2. 如果已注册仍异常，用官方原生示例记录同一RGB流的设备、系统及主机单调时间增量，再与本工具比较，区分绑定层与SDK后端。
3. 进一步用同版本Linux后端作对照，或将最小复现提交官方支持；本轮未发送消息、未提交issue、未上传现场图像或采集文件。
4. 原型保留原始字段，使用主机高精度接收时间并标明接收语义。硬件曝光同步和时序采集验收仍未完成。
